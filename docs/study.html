Module 0 - Design & Architecture

Status: complete. Architecture extended with three-tier cloud deployment design — see Module 8.

Domain choice: Research Assistant for technical papers and engineering notes. This domain gives RAG a natural job, makes citations non-negotiable, creates meaningful tool boundaries, and supports multi-agent workflows without inventing artificial complexity.

What We Are Building

The lab is a compact but production-shaped research assistant that ingests papers, RFC-style notes, and internal design documents; answers grounded questions; compares sources; extracts claims; escalates uncertain answers; and uses an external MCP server for domain-specific tools. The point is not to build the largest possible demo. The point is to make the important seams visible: ingestion, retrieval, prompting, agent tool use, graph orchestration, memory, observability, and protocol-based integration.

Research Assistant beats the other candidate domains for this lab because it exercises every module in a way that feels earned. A Developer Knowledge Base is also strong, but code-aware ingestion can pull the project toward static analysis and repository indexing before the core GenAI patterns are clear. A Support Agent is realistic, but it can hide hard retrieval questions behind simple FAQ behavior. Research work forces citation quality, semantic comparison, source metadata, ambiguity handling, and synthesis across conflicting passages.

Execution Model

LlamaIndex owns the document lifecycle: load documents, parse them into nodes, enrich metadata, embed nodes, cache transformations, and write vector records. Its ingestion pipeline is built around transformations over nodes, which is exactly the level of abstraction needed for chunking, metadata normalization, and document refresh semantics. LangChain alone can load documents and call retrievers, but LlamaIndex has a more ingestion-native execution model and stronger query engine primitives for RAG experiments.

LangChain owns the model and tool-call boundary. It gives us common chat model interfaces across providers, structured tool schemas, callbacks, retries, and agent patterns. The application code should depend on stable ports in src/genai_lab/ports/models.py and src/genai_lab/ports/vector_store.py, then adapters can translate those ports into concrete LangChain and LlamaIndex objects.

LangGraph owns long-running control flow. A simple agent loop is fine until the assistant must branch, pause for human review, retry a retrieval strategy, run multiple evaluators, checkpoint state, or prevent accidental infinite loops. Graph nodes make state transitions explicit. Edges make routing decisions inspectable. Checkpoints make failures recoverable.

Module Breakdown and Ordering

1. Document Ingestion Retrieval quality is mostly decided before the first query is asked. Chunking, metadata, refresh behavior, and embedding drift are core system design.
2. RAG Query Engine Once documents are indexed, retrieval strategies can be compared honestly. Better prompts rarely compensate for bad recall or untrusted context.
3. Tool-Using Agent Tools make sense only after the assistant has grounded knowledge to reason over. Tool contracts, error handling, and budget control determine agent reliability.
4. Stateful Multi-Agent Workflow Graph orchestration is easier to understand after one agent exists. State, routing, cycles, and interrupts are operational concerns, not decoration.
5. Memory & Persistence Memory is added after the base workflow can distinguish task state from user memory. Most memory bugs are scope bugs: storing too much, retrieving too broadly, or forgetting provenance.
6. MCP Integration External tools are most useful once local tool use and workflow routing are already clear. MCP is a contract boundary. Timeout, schema, auth, and error semantics matter.
7. Observability & Evaluation Evaluation lands last so it can trace complete workflows, not isolated functions. Agent traces need loop-aware logging, prompt versions, retrieval metrics, and cost attribution.

Major Technology Choices

Python Project Manager: uv

This project uses uv because it is fast, lockfile-oriented, and well suited to a learning lab that will add dependencies module by module. Poetry is mature and perfectly viable, but uv gives faster environment creation and simpler command ergonomics while still keeping dependency changes explicit in pyproject.toml and a future lockfile.

LlamaIndex for Ingestion and Query Engines

LlamaIndex is the right owner for ingestion because its pipeline model treats parsing, transformations, embeddings, and vector insertion as first-class steps. That matters when we later discuss chunk-size trade-offs, overlap, metadata enrichment, incremental refresh, and embedding drift. LangChain can participate at query and agent boundaries, but forcing LangChain to own ingestion would make us rebuild pipeline behavior that LlamaIndex already models well.

LangChain for Models, Tools, and Agent Primitives

LangChain provides the provider abstraction layer for chat models, common tool binding patterns, structured output, callbacks, and retry wrappers. The key design rule is that provider-specific classes stay in adapter modules. Agent logic receives a chat model, retriever, and tool list; it does not know whether the active backend is Ollama, OpenAI, Gemini, or Claude.

LangGraph for Orchestration

LangGraph is justified once the workflow has state, conditional routing, cycles, and human review. In this lab, the graph will eventually coordinate planner, retriever, answerer, verifier, and escalation nodes. A hand-written loop can be shorter, but it tends to bury control flow in mutable local variables and exception branches. LangGraph makes that control flow inspectable and testable.

PGVector in Dev, Pinecone in Prod

PGVector is the right development default because it colocates vector search with the application database, works cleanly in Docker Compose, and keeps local experimentation cheap. Pinecone is the production target because managed serverless vector infrastructure removes operational work when indexes grow, latency SLOs matter, and teams need managed scaling. The application uses a vector store port so this is a deployment decision. It should not leak into retrieval or agent code.

Spring Boot MCP Sub-Project

The MCP server is intentionally Java/Spring Boot because it simulates a realistic enterprise boundary: the Python agent layer consumes tools owned by another service and language runtime. Spring AI's MCP server support gives a typed way to expose tools and schemas while keeping the implementation behind protocol boundaries. The planned domain tools are claim normalization, citation/venue metadata lookup, and reading-list planning.

Docker Compose Topology

docker-compose.yml defines four service roles: Python app, Postgres with PGVector, Ollama, and Spring Boot MCP server. Postgres and Ollama are the default local infrastructure. The app and MCP server are profile-gated until their Dockerfiles are introduced in later modules.

For cloud deployment the single app profile splits into three independently scaled tiers: a stateless query API, a batch ingestion job, and stateless MCP replicas. The query tier and ingestion job can share the same Python image with different entrypoints. See Module 8 for the full production topology.

LLM and Vector Store Abstraction Strategy

The app has three levels of dependency:

  1. Domain services depend on ports and framework base interfaces.
  2. Adapters translate settings into LangChain, LlamaIndex, PGVector, Pinecone, and MCP clients.
  3. Settings choose providers, models, credentials, endpoints, and profile behavior.

The current skeleton establishes that boundary in src/genai_lab/config/settings.py, src/genai_lab/ports/models.py, and src/genai_lab/ports/vector_store.py. Later modules will add concrete adapters such as OllamaModelFactory, OpenAIModelFactory, PgVectorStoreFactory, and PineconeStoreFactory. The agent layer will receive model and tool instances from composition code instead of constructing them directly.

Production warning: provider abstraction is never perfect. Tool calling, streaming, JSON mode, safety filters, rate limits, context windows, and token accounting vary by provider. The interface should hide construction details, not pretend all models behave the same. Provider capability checks belong near adapter creation and test fixtures.

Configuration and Secrets

Configuration uses Pydantic Settings with an application prefix, GENAI_LAB_, and nested environment support. The default settings load .env and .env.dev; secrets are represented as SecretStr so accidental logging is less likely. .env.example documents expected keys while local secret files remain ignored by Git.

The profile model is deliberately boring: dev defaults to Ollama and PGVector, test will use deterministic or mocked adapters where possible, and prod can select OpenAI, Gemini, Claude, and Pinecone through environment variables. The app should fail fast at startup if a selected provider is missing required credentials.

Best Practices Already Applied

  • Dependency choices are recorded before implementation pressure makes them implicit.
  • Provider-neutral ports keep agent and workflow logic away from vendor constructors.
  • Settings are validated at startup rather than pulled ad hoc from os.environ.
  • Secrets are excluded from source control and represented with secret-aware types.
  • Compose separates always-needed infrastructure from future app/MCP build profiles.
  • The MCP server is modeled as an external service, not an in-process convenience function.

Gotchas, Failure Modes, and Anti-Patterns

  • Leaky provider abstraction: if graph nodes call ChatOpenAI directly, provider switching is fake.
  • Embedding drift: changing embedding models requires reindexing or versioned indexes; mixed embeddings poison retrieval.
  • Metadata afterthoughts: citations, filtering, deletion, and evaluation all depend on metadata captured during ingestion.
  • Agent loop opacity: a single while-loop hides routing, retries, and stopping conditions from tests and traces.
  • MCP without contracts: tool schemas, timeouts, and error shapes must be treated as API design, not glue code.
  • Local/prod mismatch: Ollama and hosted frontier models differ in context limits, tool reliability, latency, and instruction following.

Source Notes

The design aligns with current official documentation for LlamaIndex ingestion pipelines, LangChain provider/model abstractions, Spring AI MCP, PGVector, Pinecone serverless architecture, and Pydantic Settings.

Quiz

1. Why does LlamaIndex own ingestion instead of LangChain?

Because ingestion is a pipeline of loading, node parsing, transformation, metadata enrichment, embedding, caching, and vector insertion. LlamaIndex models those steps directly, while LangChain is better used here for model/tool abstractions and agent behavior.

2. What is the main architectural reason to introduce LangGraph?

Stateful orchestration. Once the system needs conditional routing, cycles, retries, checkpoints, and human interrupt points, graph structure makes control flow explicit and testable.

3. Why is PGVector a better dev default than Pinecone?

It runs locally inside the same Docker Compose stack as Postgres, keeps experiments cheap, and colocates relational and vector data. Pinecone becomes attractive when production scale, managed operations, and latency SLOs matter.

4. What is the danger of switching embedding models without reindexing?

The vector space changes. Queries embedded by the new model are compared against chunks embedded by the old model, which can silently degrade retrieval quality.

5. What should the provider abstraction hide, and what should it not hide?

It should hide construction, credentials, endpoint selection, and common invocation setup. It should not hide real capability differences such as context windows, tool calling behavior, streaming support, JSON reliability, latency, or token pricing.

Module 1 - Document Ingestion Pipeline

Status: implemented and verified with a LlamaIndex dry run.

What changed: the project now has a real LlamaIndex ingestion pipeline for research documents, sample source material, metadata enrichment, chunking policy validation, optional embeddings, PGVector indexing hooks, persistent ingestion caching, and a CLI entry point.

What Was Built

Module 1 adds the ingestion layer under src/genai_lab/ingestion. The CLI in src/genai_lab/ingestion/cli.py calls run_ingestion, which loads files from data/research_notes, turns them into LlamaIndex documents, parses them into nodes, and either stops after parsing for --dry-run or continues through embedding and PGVector insertion for a full indexing run.

The sample corpus is intentionally small: rag_failure_modes.md and agentic_workflows.md. They are not toy lorem ipsum. They contain the concepts the later modules will retrieve against: RAG failure modes, chunking trade-offs, embedding drift, graph workflow design, human review, and tool schema quality.

Execution Model Under the Hood

LlamaIndex ingestion has three conceptual stages: load, transform, and store. Loading uses SimpleDirectoryReader in load_documents. That reader walks the source directory, applies extension filters, creates Document objects, and attaches the metadata returned by our file_metadata callback. That callback is important: it is the earliest reliable moment to attach source identity before text is split into chunks.

Transformation happens inside IngestionPipeline. In dry-run mode, the pipeline has one transformation: SentenceSplitter. In full indexing mode, the pipeline appends an embedding transformation created by create_embedding_model. That ordering matters: embedding must happen after node parsing, because the vector store should receive vectors for chunks, not whole unbounded documents.

Storage is optional at runtime. When --dry-run is used, the pipeline returns parsed nodes and writes only the ingestion cache. In full mode, create_pgvector_store parses the configured Postgres DSN and creates a LlamaIndex PGVectorStore. The vector store is attached directly to IngestionPipeline, so pipeline.run both computes embeddings and writes vector records. 

CLI
  -> Settings
  -> ChunkingProfile.validate()
  -> SimpleDirectoryReader(file_metadata=build_source_metadata)
  -> IngestionPipeline(
       SentenceSplitter,
       [OllamaEmbedding or OpenAIEmbedding],
       [PGVectorStore],
       IngestionCache
     )
  -> nodes returned, cache persisted, vectors written in full mode

Design Decisions

Dry Run Is a First-Class Path

The CLI supports --dry-run because production ingestion needs a way to inspect parsing and metadata before spending money or mutating an index. This also keeps local verification fast: Module 1 was verified by loading 2 documents and producing 2 nodes without requiring Ollama or Postgres to be running.

Chunking Policy Is Explicit

ChunkingProfile in chunking.py validates chunk size and overlap before the LlamaIndex parser is constructed. The default is 512 tokens with 80 tokens of overlap. That is a pragmatic starting point for research prose: large enough to preserve a local argument, but small enough to avoid stuffing the answer context with unrelated paragraphs.

Metadata Is Attached Before Chunking

build_source_metadata records source path, source file name, source type, corpus, and ingestion timestamp. Later RAG modules will need this metadata for citations, filters, deletion/reindexing, evaluation slices, and debugging bad answers. Metadata added after chunking is usually less reliable because the relationship between chunk and source has already become indirect.

Embedding Provider Is Config-Selected

Module 1 supports Ollama and OpenAI embeddings. The default remains local Ollama with nomic-embed-text. OpenAI is wired because production and evaluation profiles often use hosted embeddings, but provider choice stays in Settings, not in ingestion business logic.

PGVector Is the First Concrete Store

The ingestion module writes to PGVector for the development profile because it is local, reproducible, and colocated with the application database. Docker Compose now mounts docker/postgres/init/001_enable_pgvector.sql so fresh Postgres volumes enable the vector extension at initialization.

Best Practices Applied

  • Run parsing separately from indexing so bad chunks can be caught before expensive writes.
  • Attach source metadata at reader time, before documents are split into nodes.
  • Validate chunking settings explicitly instead of letting bad parser parameters fail deep inside the framework.
  • Persist an ingestion cache so repeated runs do not recompute stable transformations unnecessarily.
  • Keep embedding provider selection in configuration and factory functions.
  • Initialize PGVector through Compose so local setup is reproducible.

Gotchas and Failure Modes

  • Embedding drift: changing from nomic-embed-text to another embedding model changes the vector space. Reindex or partition by embedding version.
  • Dimension mismatch: PGVector tables are created with a fixed embedding dimension. GENAI_LAB_EMBEDDING_DIMENSION must match the active embedding model.
  • Overlapping too much: high overlap improves continuity but inflates storage, embedding cost, and duplicate retrieval.
  • Chunking too small: tiny chunks retrieve precise snippets but often lose definitions, caveats, and experimental setup.
  • Silent metadata loss: citations and deletion workflows become painful if source path and corpus metadata are not attached before parsing.
  • Assuming local equals prod: Ollama embeddings are excellent for local development, but production quality and latency should be evaluated against the hosted profile before deployment decisions.

Quiz

1. Why should metadata be attached before chunking?

Because every resulting node inherits source identity. That makes citation, filtering, deletion, and debugging possible without reconstructing provenance later.

2. Why is dry-run ingestion useful in production?

It lets engineers inspect loaded documents, chunk counts, and metadata before spending embedding budget or mutating the vector index.

3. What operational problem does embedding drift create?

Old chunks and new queries may live in incompatible vector spaces. The system can still return results, but relevance silently degrades.

4. What trade-off does chunk overlap create?

Overlap preserves context across chunk boundaries, but too much overlap increases duplicate content, storage volume, embedding cost, and repeated retrieval.

5. Why must PGVector know the embedding dimension?

The vector column has a fixed dimensionality. If the embedding model outputs vectors of a different size, inserts or similarity search will fail.

Module 2 - RAG Query Engine

Status: implemented and verified with local retrieval and deterministic synthesis.

What changed: the project now has a RAG query engine with retrieval strategies, query transforms, citation objects, prompt-injection screening, context budgeting, a local no-service execution path, and PGVector-backed LlamaIndex retrieval wiring.

What Was Built

Module 2 adds src/genai_lab/rag. The main entry point is RagQueryEngine in engine.py. It accepts a question, expands it into retrieval queries, retrieves evidence, screens retrieved text as untrusted data, applies a context budget, synthesizes an answer, and returns citations plus warnings.

The engine has two paths. The verified local path uses LocalCorpusRetriever over the source files in data/research_notes. That path does not need Ollama, Postgres, or an API key, which makes tests and study runs stable. The production-shaped path creates a LlamaIndex VectorStoreIndex from PGVector and maps our retrieval strategy to LlamaIndex vector query modes.

Execution Model Under the Hood

A RAG query is a pipeline, not a single call. First, build_query_variants creates one or more retrieval queries. none uses the original question. step_back adds a broader conceptual query. hyde adds a hypothetical-answer query. In this module those transforms are deterministic so the system can be tested without a model call, but the prompt contracts are defined with LangChain ChatPromptTemplate so later modules can swap in model-generated rewrites.

Retrieval then runs against either the local corpus or PGVector. Local retrieval uses the same LlamaIndex SentenceSplitter as ingestion, then scores nodes with a simple IDF-like lexical score. This is not pretending to be semantic vector search; it is a deterministic harness for exercising ranking, citations, and safety behavior. The PGVector path uses VectorStoreIndex.from_vector_store with the configured embedding model. 

Question
  -> QueryTransform: none | step_back | hyde
  -> RetrievalStrategy: similarity | mmr | hybrid
  -> Rerank / diversify
  -> Prompt-injection screen
  -> Context token budget
  -> Answer synthesis
  -> Citation objects + warnings

Retrieval Strategies

similarity ranks by relevance score and returns the top chunks. This is the lowest-latency baseline and is the first strategy to benchmark. mmr uses maximal marginal relevance to penalize chunks that duplicate already selected evidence. It is useful when the corpus contains repeated claims or many near-identical sections. hybrid is the production target for queries that mix exact terminology with semantic intent. In the local path it combines lexical scoring with exact-query bonuses; in the vector path it maps to LlamaIndex's hybrid vector-store query mode.

Reranking and Context Budgeting

Module 2 includes lightweight reranking behavior through MMR and rerank_top_n. This is where production systems usually decide whether to add a cross-encoder reranker. A reranker can improve answer quality by moving the best evidence to the top, but it adds latency and often an extra model dependency. For a research assistant, the right pattern is usually: retrieve more than you need, rerank down to the strongest few chunks, then enforce a context budget before synthesis.

Citation Handling

The engine returns explicit Citation objects with source id, source file, path, score, snippet, and safety flags. The deterministic answer uses bracket citations such as [1]. In the PGVector path, the code also imports LlamaIndex CitationQueryEngine to document the intended model-backed citation pattern. We use RetrieverQueryEngine there for now because Module 2 also needs query variants and strategy-level control.

Prompt Injection from Documents

Retrieved documents are untrusted input. A paper, README, ticket, or scraped page can contain text that looks like instructions to the model. Module 2 adds screen_context in security.py to flag common patterns such as "ignore previous instructions", role-confusion language, system-prompt references, and secret-exfiltration bait. This is not a complete defense. It is an operational tripwire and a teaching point: RAG does not remove prompt injection risk because retrieved text shares the model's context window with real instructions.

Best Practices Applied

  • Separate retrieval strategy from answer synthesis so ranking can be evaluated independently.
  • Return citations as structured data, not only text appended to an answer.
  • Keep a deterministic local path so retrieval behavior is testable without model variance.
  • Screen retrieved context before synthesis and surface warnings with the answer.
  • Budget context explicitly instead of passing every retrieved chunk to the model.
  • Use query transforms as configurable retrieval behavior, not hidden prompt magic.

Gotchas and Failure Modes

  • Retrieval quality vs latency: hybrid search, query expansion, and reranking can improve recall, but every extra step adds latency and cost.
  • Query expansion drift: HyDE and step-back prompting can retrieve broader evidence, but they can also move away from the user's actual question.
  • Citation theater: bracket citations are not proof unless citations point to the exact retrieved evidence used by synthesis.
  • Context flooding: too many chunks can degrade answer quality because the model must choose among weak, duplicated, or conflicting evidence.
  • False safety confidence: regex screening catches obvious prompt-injection patterns, not adversarial hidden text or subtle instruction laundering.
  • Hybrid mismatch: local hybrid scoring is a test harness; production hybrid behavior depends on vector-store capabilities and sparse-index configuration.

Quiz

1. Why is retrieval evaluated separately from answer generation?

Because a fluent model can hide bad retrieval. If the right evidence is not retrieved, synthesis quality is mostly damage control.

2. What problem does MMR solve?

It trades a little raw relevance for diversity, reducing near-duplicate chunks and improving coverage of distinct evidence.

3. When can HyDE hurt retrieval?

When the hypothetical answer introduces terms or assumptions that are not actually part of the user's question, pulling retrieval toward plausible but irrelevant evidence.

4. Why are retrieved documents treated as untrusted input?

Because they can contain instructions, hidden prompts, or exfiltration bait. The model sees that text in the same context window as real instructions.

5. What makes citations meaningful rather than decorative?

They must point to the exact retrieved evidence used in the answer, with stable source metadata and enough snippet context for auditability.

Module 3 - Tool-Using Agent

Status: implemented and verified with a local bounded tool loop.

What changed: the project now has LangChain custom tools, explicit Pydantic tool schemas, a bounded ReAct-style local executor, structured final output, retry-aware tool error handling, token budget checks, a CLI, and an optional LangChain create_agent factory for model-backed runs.

What Was Built

Module 3 adds src/genai_lab/agents. The tool layer in tools.py exposes three LangChain tools: rag_search, compare_sources, and citation_lookup. The local executor in executor.py runs a small ReAct-style loop: choose an action, call a tool, observe the result, track the trace, and produce a structured ResearchAgentResponse.

This module deliberately separates two concerns. The local executor is deterministic and testable without an LLM. The optional create_model_backed_agent factory in langchain_agent.py uses LangChain's modern create_agent runtime and the same tool list. That keeps the study path runnable while still showing the production integration point for a provider-backed model.

Execution Model Under the Hood

LangChain tools are callable objects with names, descriptions, and argument schemas. In this module, each tool has a Pydantic input model. The schema is not only validation; it is also the contract a model sees when deciding whether and how to call a tool. Tool descriptions are part of the control plane. Vague descriptions cause vague tool calls. 

User task
  -> Planner chooses next action
  -> Tool schema validates input
  -> Tool executes with retry boundary
  -> Observation is recorded in trace
  -> Budget / iteration limits are checked
  -> Structured final response is validated by Pydantic

LangChain's current create_agent builds a graph-backed agent runtime using LangGraph internally. A model node decides whether to call tools or finish; a tools node executes selected tools; the loop continues until a final response or stop condition. Module 3's local executor mirrors those mechanics without pretending to be a substitute for a reasoning model.

Custom Tools

  • rag_search: calls the Module 2 RAG engine and returns JSON with answer, citations, and warnings.
  • compare_sources: compares two known corpus files for contrast-style questions.
  • citation_lookup: verifies source provenance and returns a short excerpt.

These tools are intentionally narrow. A good tool does one thing, names its inputs clearly, and returns a boring shape. The agent should not need to reverse-engineer prose to understand whether a call succeeded.

Structured Output

The final response is a Pydantic ResearchAgentResponse with status, answer, citations, tools_used, and warnings. This is the shape downstream APIs and future LangGraph nodes should consume. Free-form text is fine for display; structured output is what keeps orchestration sane.

Error Handling, Retries, and Fallbacks

Tool calls are wrapped at the executor boundary. A failing tool records one trace per attempt and is retried up to agent_tool_retry_attempts. If retries are exhausted, the agent does not hallucinate a successful answer. It returns needs_review with a tool failure warning. That is a fallback chain in the operational sense: when automation cannot complete safely, route to a recoverable state instead of continuing the loop blindly.

The executor also enforces agent_max_iterations and agent_token_budget. Token budgeting here is approximate, but the design lesson matters: agents need loop limits and context limits before they are trusted with real user traffic.

Module 4 - Stateful Multi-Agent Workflow

Status: implemented and verified with LangGraph checkpointed execution.

What changed: the project now has a LangGraph state machine that coordinates planner, evidence worker, risk worker, synthesizer, verifier, human-review interrupt, and finalizer nodes. It uses typed shared state, conditional routing, parallel worker fan-out, checkpointing, interrupts, and explicit cycle limits.

What Was Built

Module 4 adds src/genai_lab/workflows. The graph in graph.py is a supervisor-style workflow for research answers. It starts with a planner, fans out to evidence retrieval and risk assessment workers, merges those results in synthesis, verifies confidence, optionally interrupts for human review, then finalizes the answer.

This is the point where an "agent" becomes a system. Module 3 could call tools and return an answer. Module 4 decides when tool output is enough, when risk requires a human, where retry cycles are allowed, and how state survives across an interrupt.

Execution Model Under the Hood

LangGraph runs the workflow as a stateful graph. Each node receives the current ResearchWorkflowState and returns a partial state update. Fields such as evidence, citations, risk_flags, and audit_log use reducer annotations so parallel branches can safely append to shared state instead of overwriting each other. 

START
  -> plan_task
  -> [retrieve_evidence, assess_risk]   # fan-out workers
  -> synthesize_answer                  # fan-in
  -> verify_answer
     -> human_review interrupt          # if risky or low confidence
     -> plan_task                       # if retry is allowed
     -> finalize
  -> END

The graph is compiled with InMemorySaver, which gives each invocation a checkpoint thread. The CLI creates a thread id for each run. Tests use fixed thread ids so an interrupted workflow can be resumed with Command(resume="approved").

Supervisor Pattern

The planner and verifier act as supervisors. The planner writes the high-level plan and cycle count. The verifier decides whether to finalize, retry, or interrupt. The worker nodes do not decide global control flow; they do specialized work and report evidence or risk signals. This separation is what keeps multi-agent systems from turning into several agents all trying to be in charge at once.

Parallel Node Execution

route_after_plan returns both retrieve_evidence and assess_risk. LangGraph schedules them in the same graph step. Their outputs are merged through reducers in the state schema. In a production deployment these workers could be expensive and independent: one might call retrieval tools while another runs policy checks or evaluates the user request.

Human-in-the-Loop Interrupts

The human_review node calls LangGraph's interrupt function with the draft answer, risk flags, confidence, and review request. The graph stops and preserves state in the checkpointer. A caller can resume with a decision such as approved, revise, or rejected. This is the right pattern for review gates: pause with context, then resume from the same state instead of replaying the whole workflow.

Cycle Detection and Checkpointing

The state tracks cycle_count and max_cycles. Retry loops are useful, but unbounded agent loops are an outage pattern. Module 4 keeps the loop small and visible. The checkpoint thread id is also explicit, which matters later for persistence, auditability, and resuming long-running workflows.

  • src/genai_lab/workflows/graph.py: graph nodes, conditional edges, interrupts, and compilation.
  • src/genai_lab/workflows/cli.py: workflow CLI and checkpoint thread ids.
  • tests/test_workflow_graph.py: finalization, interrupt/resume, and graph-shape tests.

Best Practices Applied

  • Use typed shared state so node contracts are visible.
  • Keep supervisor routing separate from worker execution.
  • Use reducers for state fields updated by parallel branches.
  • Interrupt with enough context for a human to make a decision.
  • Use checkpoint thread ids for resumability and audit trails.
  • Put hard limits on cycles before adding more autonomous behavior.

Gotchas and Failure Modes

  • Reducer mistakes: parallel branches that write the same key need reducers or one branch can overwrite another.
  • Supervisor confusion: if every node routes globally, the graph becomes harder to reason about than a plain loop.
  • Interrupt without context: a human-review gate is useless if it omits the draft, risk reason, or confidence signal.
  • Unbounded retries: agentic cycles need explicit stop conditions and audit logs.
  • Checkpoint identity drift: resuming requires the same thread id and checkpointer; otherwise the workflow cannot recover prior state.
  • Hidden side effects: irreversible tool calls should happen behind review gates or idempotent write patterns.

Quiz

1. Why does shared graph state need reducers?

Parallel nodes may update the same key in the same graph step. Reducers define how those updates merge instead of overwriting each other.

2. What is the supervisor pattern buying us?

It centralizes routing decisions in planner/verifier nodes while worker nodes focus on specialized tasks, making control flow easier to test and inspect.

3. Why is an interrupt better than returning "ask a human" text?

An interrupt preserves workflow state and pauses execution at the exact review point, so the graph can resume without replaying expensive or side-effectful steps.

4. What failure mode does cycle_count prevent?

Unbounded retry loops, where agents keep planning, retrieving, or revising without a clear stop condition.

5. Why do checkpoint thread ids matter?

They identify the saved workflow state. Resuming an interrupted or long-running graph requires the same thread id and checkpointer.

Module 5 - Memory & Persistence

Status: updated — profile-based backend selection: InMemoryStore for dev/test, PostgreSQL+pgvector for prod.

What changed: the project now has a memory subsystem with bounded short-term conversation memory, deterministic summarization, scoped long-term memory, semantic/episodic/entity memory types, a BaseMemoryStore ABC with two concrete backends (LongTermMemoryStore for dev, PgLongTermMemoryStore for prod), profile-driven backend selection in MemoryManager.create(), a memory_table_sql() DDL helper, a CLI demo, and tests.

What Was Built

Module 5 adds src/genai_lab/memory. The main facade is MemoryManager, which coordinates a ConversationBuffer for short-term thread memory and a BaseMemoryStore implementation for durable user-scoped memory. It can store conversation turns, remember semantic facts, extract entity memories, and build a prompt-ready MemorySnapshot.

The memory subsystem is intentionally conservative. It does not automatically stuff every prior conversation into the prompt. It stores scoped records, retrieves only a small relevant set, and keeps summaries separate from raw turns. That separation matters because memory bugs usually become privacy, relevance, or cost bugs.

Execution Model Under the Hood

Short-term memory is the current thread's working context. ConversationBuffer stores recent turns and creates a rolling summary when the token estimate crosses a threshold. The summary is deterministic in this module so tests remain stable. In a model-backed system, the same boundary would call a summarization chain with strict instructions to preserve facts, decisions, open questions, and user preferences.

Long-term memory is backed by one of two concrete stores, selected at construction time by MemoryManager.create() based on settings.profile. Both stores implement the same BaseMemoryStore ABC and use lexical ranking for search. The point is the interface: graph checkpoints preserve thread state, while the store persists memories across threads — and that interface now works in both profiles without changing any caller code. 

Conversation turn
  -> short-term buffer
  -> summarize if budget is exceeded
  -> episodic memory record
  -> entity extraction
  -> entity memory records

User preference or durable fact
  -> semantic memory record

New task
  -> render short-term context
  -> retrieve semantic + episodic memories
  -> retrieve entity memories
  -> build MemorySnapshot

Backend Selection by Profile

MemoryManager.create(settings, user_id=...) reads settings.profile and constructs the appropriate backend. Callers never touch the backend directly — they go through MemoryManager, which delegates to whichever store was selected. 

settings.profile == PROD
  -> PgLongTermMemoryStore(dsn, embedding_dimension)
       psycopg.connect(dsn)
       _ensure_table() — runs memory_table_sql(embedding_dimension) DDL
       put()    — INSERT ... ON CONFLICT DO UPDATE
       search() — SELECT by user_id + kind, lexical-ranked in Python

settings.profile == DEV | TEST (default)
  -> LongTermMemoryStore()
       InMemoryStore() (LangGraph in-process store)
       put()    — store.put(namespace, key, value)
       search() — store.search(namespace), lexical-ranked in Python

Both share BaseMemoryStore:
  persist_turn()          — writes EPISODIC + ENTITY records
  remember_semantic_fact() — writes SEMANTIC record

BaseMemoryStore is an abstract base class with put() and search() as abstract methods. The shared logic — persist_turn() and remember_semantic_fact() — lives in the base class and calls self.put(), so it does not need to be duplicated across backends.

PgLongTermMemoryStore uses lexical ranking (the same _lexical_score used by the InMemory backend) for now. When the embedding adapter is wired in deployment Phase 4, the search() method can be updated to issue a pgvector cosine similarity query instead — the agent_memory table and HNSW index are already created by memory_table_sql().

Memory Types

  • Short-term memory: recent conversation state for the active thread. Useful for local coherence and unresolved references.
  • Semantic memory: durable facts and preferences, such as "the user prefers trade-off explanations."
  • Episodic memory: past interactions and outcomes, useful when the agent needs to remember what happened before.
  • Entity memory: named people, systems, tools, projects, or concepts that recur across tasks.
  • Procedural memory: reusable instructions or skills. Module 5 models the category but does not yet add writable procedural memory.

LangChain Memory Abstractions

Older LangChain memory classes such as conversation buffer memory are no longer the best anchor for production agent systems. Modern LangChain and LangGraph push memory toward explicit graph state, checkpointing, stores, and message history boundaries. That is the right direction: agent tool calls, structured outputs, interrupts, and long-running workflows need memory to be visible in state and persistence layers, not hidden in a chain object.

PGVector as Memory Store

pgvector_design.py exports memory_table_sql(embedding_dimension), which returns the DDL for the agent_memory table: id, user_id, agent_id, kind, text, metadata (JSONB), embedding (VECTOR(n)), created_at, and last_accessed_at. PgLongTermMemoryStore._ensure_table() calls this at construction time, so the table and its indexes (a B-tree scope index and an HNSW cosine index) are created automatically when the prod store is first instantiated. The embedding dimension is read from settings.embedding_dimension and must match the active embedding model. In production, semantic search should filter by user_id and kind before ranking by vector similarity. The same Postgres/PGVector instance can support both document chunks and memory records, but they should live in separate tables because they have different lifecycles, deletion semantics, and privacy rules.

Summarization Strategy

Summarization is a compression policy, not a cleanup chore. A useful memory summary preserves stable preferences, decisions, constraints, unresolved questions, and commitments. It should not preserve every tool output. Module 5 summarizes older turns when the short-term buffer crosses a token threshold, then keeps the latest turn raw. That gives the next agent step both continuity and recency.

Best Practices Applied

  • Scope memory by user and agent to prevent cross-user leakage.
  • Separate checkpoints, short-term memory, and long-term memory.
  • Store memory records with kind and metadata so retrieval can filter before ranking.
  • Summarize old turns instead of replaying unbounded history.
  • Keep entity memory conservative to avoid polluting future prompts.
  • Put shared write logic (persist_turn, remember_semantic_fact) in the ABC so backends only implement storage, not business rules.
  • Lazy-import the prod store in MemoryManager.create() so dev/test runs never attempt a DB connection.

Gotchas and Failure Modes

  • Memory poisoning: user-provided content can become persistent instruction if writes are not filtered.
  • Cross-domain leakage: memories from one task or user can inappropriately influence another if scope is wrong.
  • Context bloat: loading too many memories is just a slower version of loading the whole chat history.
  • Stale preferences: durable facts need update and deletion semantics, not only append behavior.
  • Embedding drift: memory vectors need the same embedding-version discipline as document vectors.
  • Summary loss: bad summaries can erase caveats or invent continuity that never happened.

Quiz

1. Why separate short-term and long-term memory?

Short-term memory supports the active thread; long-term memory persists across threads. Mixing them causes context bloat, stale recall, and privacy problems.

2. What should semantic memory store?

Durable facts, preferences, and stable user or domain knowledge that should be retrievable in future sessions.

3. Why is user scoping mandatory?

Without user scope, one user's preferences or sensitive history can leak into another user's context.

4. Why is summarization risky?

A summary can drop caveats, overstate certainty, or invent continuity. It must preserve decisions, constraints, and unresolved questions carefully.

5. Why should document vectors and memory vectors live separately?

They have different lifecycles, privacy rules, deletion needs, metadata, and retrieval semantics, even if both use PGVector under the hood.

6. Why does shared logic like persist_turn live in BaseMemoryStore rather than in each backend?

Because the business rules for what to write (episodic record + entity records per turn) do not depend on how data is stored. Backends only need to implement put() and search(); the ABC composes them into higher-level operations without duplicating logic.

7. Why is PgLongTermMemoryStore lazy-imported inside MemoryManager.create() rather than at the top of manager.py?

So that importing the manager module never triggers a psycopg import or any connection attempt. Tests and dev-profile runs never pay the cost of loading prod dependencies they won't use.

Why LangSmith

Module 7 chooses LangSmith over LangFuse for the primary tracing and prompt-versioning story because this project is already built around LangChain and LangGraph. LangSmith gives automatic tracing hooks for LangChain agents and LangGraph workflows, plus prompt management, datasets, and evaluations in the same ecosystem. LangFuse is a strong open-source option and would be a reasonable production choice for teams that want self-hosting or vendor-neutral OpenTelemetry pipelines first. For this lab, LangSmith reduces integration friction and lets the study path focus on agent/RAG failure analysis rather than instrumentation plumbing.

What Was Built

src/genai_lab/observability contains the tracing and prompt-versioning layer. JsonlTraceWriter writes append-only JSONL events for local development and CI. It redacts sensitive-looking keys before writing. build_langsmith_environment returns the environment contract needed to enable LangSmith without mutating global process state. PromptRegistry registers prompt ids such as rag-answer-v1 and agent-supervisor-v1, which is the local counterpart to LangSmith prompt commits.

src/genai_lab/evaluation contains a deterministic RAG evaluation runner. The dataset lives in data/evaluation/rag_eval_set.jsonl. Each case has a question, a reference answer, and required terms. The runner calls the local RAG engine, then scores the result for faithfulness, answer relevance, context recall, citation coverage, and a weighted overall score.

Execution Model Under the Hood

Production observability is not just logs. A useful trace has a stable run id, span names, inputs, outputs, timing, status, metadata, and enough structure to join retrieval, model calls, tools, workflow nodes, memory reads, and MCP calls. In LangChain/LangGraph production paths, LangSmith can capture those spans automatically when tracing is enabled. In local deterministic paths, the JSONL writer captures the same kind of event shape so tests and examples stay inspectable. 

request
  -> RAG / agent / graph entrypoint
  -> local TraceEvent or LangSmith run
     -> inputs: question/task, tool args after redaction
     -> outputs: answer preview, citations, warnings, tools used
     -> metadata: prompt version, retrieval strategy, provider profile
  -> evaluation runner
     -> faithfulness
     -> answer relevance
     -> context recall
     -> citation coverage

The local evaluation metrics are deliberately lightweight. They use lexical overlap rather than an LLM judge, so they are not a substitute for RAGAS in production. They are a CI gate: if a retrieval change stops surfacing key evidence, citation coverage disappears, or an answer drifts away from the question, the suite should flag it cheaply and deterministically. For production, this same dataset should be promoted into LangSmith or RAGAS with model-judged faithfulness and context recall.

Prompt Versioning Strategy

Prompts are versioned by id, not by file name alone. The id appears in trace metadata so an evaluation failure can be tied back to the exact prompt contract used for a run. In production, prompt edits should be committed in LangSmith, tagged by environment, and rolled out through a profile flag. The anti-pattern is changing a prompt string inline and then trying to explain a quality regression from application logs alone.

Agentic Loop Logging

Agent logs must expose decision quality without leaking secrets or drowning operators. The useful grain is one event per loop or tool call: chosen tool, attempt number, bounded input summary, bounded output summary, status, retry count, token budget pressure, and final routing decision. Avoid logging full prompts, raw retrieved documents, API keys, or entire memory payloads by default. The local trace writer uses preview fields and redaction because a trace system that becomes a shadow data lake is a production incident waiting to happen.

Gotchas and Failure Modes

  • Trace leakage: traces often contain user data, retrieved documents, and tool payloads. Treat them as sensitive production data.

  • Agent loop spam: logging every token or full prompt makes traces expensive and hard to inspect.
  • Offline metric limits: lexical metrics miss paraphrases and can reward copied context, so they are a smoke alarm, not a judge.

Quiz

1. Why keep a local JSONL trace sink if LangSmith is the production choice?

It keeps tests deterministic, supports offline development, and preserves the same event shape before credentials or network services are available.

2. Why put prompt version ids in trace metadata?

Quality regressions need to be tied to the prompt contract that produced them. Without prompt version metadata, tracing cannot explain prompt drift.

3. What is faithfulness measuring?

Whether answer claims are supported by retrieved context. It is different from general factual correctness.

4. Why are lexical local metrics not enough for production RAG evaluation?

They miss paraphrases, cannot reason over claims, and can reward copied context. Production evaluation should add model judges, calibration sets, and human review.

5. What should agentic loop logs avoid?

Full secrets, unbounded prompts, raw retrieved documents, and unlimited memory/tool payloads. Logs should be bounded, redacted, and useful for debugging decisions.

Module 8 - Cloud Deployment at Scale

Status: architecture defined. Full phase checklist in docs/deployment-implementation-plan.md.

What this adds: the lab is deployable beyond a single laptop. The local Docker Compose topology is refactored into three independently scaled tiers — a stateless query API, a batch ingestion job, and stateless MCP replicas — backed by managed cloud services for LLM calls, vector search, and memory persistence.

Why Three Tiers, Not One App

The single app container in docker-compose.yml is a local convenience, not a production shape. Query traffic and ingestion workloads have fundamentally different scaling profiles: queries need fast interactive latency and autoscale on RPS; ingestion needs high throughput over large documents, runs as a scheduled or event-triggered job, and does not need to be always-on. Running them in the same process means scaling one forces scaling both, which is expensive and operationally coupled.

The Spring Boot MCP server (ResearchToolService) exposes pure functions with no database or shared state. It is trivially horizontally scalable and belongs behind its own load balancer, independent of the query and ingestion tiers.

Cloud Architecture

                ┌──────────────────────────────────────────────────────────┐
 Users → API GW/LB → Query service  (stateless, autoscaled on RPS/latency)
                │        = FastAPI wrapping RAG engine / LangGraph workflow / agent
                │              │               │                      │
                │       Managed LLM      Vector store           Memory store
                │       + embeddings     (pgvector/Pinecone)    (Postgres+pgvector)
                │              │
                │       MCP server (stateless Spring, N replicas behind LB)
                └──────────────────────────────────────────────────────────┘

 Doc upload → Object store → (event / schedule) → Ingestion JOB → vector store

The query tier and ingestion job can share the same Python Docker image with different entrypoints: the query service runs uvicorn (Phase 2 FastAPI app), and the ingestion job runs python -m genai_lab.ingestion.cli. Same image, different lifecycle.

Phase Plan

Phase 0 — Foundations (infra + CI/CD)

Choose cloud (AWS or GCP) and define dev, staging, and prod environments mapping to RuntimeProfile. Provision IaC (Terraform or CDK): VPC, managed Postgres+pgvector, object store, secret manager, image registry, and load balancer. Build pipeline publishes the Python image (query + ingestion entrypoints) and the Java MCP image. Move secrets from .env into the secret manager; existing SecretStr fields (postgres_dsn, *_api_key) load them transparently via the GENAI_LAB_-prefixed environment variables.

Phase 1 — Externalize Long-Term Memory ✓ implemented

Done. PgLongTermMemoryStore in memory/store.py provides a PostgreSQL+pgvector-backed implementation behind the BaseMemoryStore ABC. MemoryManager.create() selects it when settings.profile == PROD and falls back to the LangGraph InMemoryStore backend for dev and test. The agent_memory table (with scope index and HNSW cosine index) is created automatically on first connection via memory_table_sql(embedding_dimension). MemoryNamespace scoping is preserved — user_id is extracted from the namespace tuple so per-user isolation holds across replicas.

Remaining: replace lexical ranking in PgLongTermMemoryStore.search() with a pgvector cosine similarity query once the embedding adapter lands in Phase 4. The table schema and HNSW index are already in place for that upgrade.

Phase 2 — HTTP API for the Query Tier

Add a FastAPI/uvicorn application exposing the RAG engine, agent, and LangGraph workflow as HTTP endpoints. This becomes the query-tier container entrypoint — currently everything is CLI-only. Keep request handling stateless; all durable state lives in the memory store and vector store. Add /healthz and /readyz probes for load-balancer health checks. Pass user_id per request so MemoryNamespace scoping and per-user memory retrieval work correctly.

Phase 3 — Split Ingestion into a Job

Make ingestion a separate container entrypoint or cloud job, not part of the always-on query service. Read source documents from object storage instead of the local ingestion_input_dir. Trigger on upload event or schedule; write chunks and embeddings to the managed vector store. Reuse the LlamaIndex ingestion cache where possible; make re-runs idempotent so a crashed or retried job does not duplicate chunks.

Phase 4 — Managed LLM and Vector Store

Implement ChatModelFactory and EmbeddingModelFactory adapters for the cloud LLM provider: Bedrock (Claude) on AWS, Vertex AI on GCP. Select via GENAI_LAB_LLM_PROVIDER. Retire Ollama for the prod profile. Point retrieval at managed Postgres+pgvector or Pinecone via GENAI_LAB_VECTOR_STORE_PROVIDER. Tune rag_top_k, rag_rerank_top_n, and rag_context_token_budget against the managed model and load-test end-to-end latency.

Phase 5 — Scale the MCP Server

ResearchToolService tools are pure functions with no shared state. Run N stateless replicas behind a load balancer. Add Spring Boot Actuator health probes and point the query service's GENAI_LAB_MCP_SERVER_URL at the load-balancer address. No persistence layer is needed.

Phase 6 — Observability, Scaling, and Ops

Ship JsonlTraceWriter traces to CloudWatch Logs or Cloud Logging (or enable LangSmith via GENAI_LAB_LANGSMITH_TRACING=true). Autoscale the query API on RPS and latency; MCP server on CPU; ingestion as on-demand or scheduled cloud jobs. Add alarms for query 5xx rate, p95 latency, model latency and cost, DB connection pool saturation, and ingestion job failures. Capacity-plan the managed LLM endpoint (provisioned throughput) for expected concurrent user load.

Suggested Execution Order

Phase 1 (memory externalization) is complete. Remaining order: Phase 0 (IaC/CI) → Phase 2 (HTTP API) → Phase 4 (managed LLM/vectors, including wiring vector search into PgLongTermMemoryStore) → Phase 3 (ingestion job) → Phase 5 (MCP replicas) → Phase 6 (ops).

Explicit Non-Goals and Pitfalls

  • Phase 1 (memory externalization) is complete — running multiple query replicas is now safe as long as GENAI_LAB_PROFILE=prod and a shared Postgres instance is configured.
  • Do not bundle ingestion into the always-on query service — it is a batch job with a different scaling shape.
  • Keep the deterministic dry-run paths and the evaluation suite green as model-backed adapters replace Ollama and local retrieval stubs.
  • Provider-neutral ports (VectorStoreFactory, model adapter factories) must stay clean — switching from Ollama to Bedrock should be a settings change, not a code rewrite.

Quiz

1. Why must long-term memory be externalized before running more than one query replica?

Because InMemoryStore is not shared across processes. A user hitting different replicas would see different or missing memory, making per-user behavior inconsistent.

2. Why is ingestion a separate job instead of part of the always-on query service?

Ingestion is a batch workload triggered by document uploads or schedules. Bundling it into the query service couples two completely different scaling shapes — interactive RPS versus document throughput — forcing both to scale together unnecessarily.

3. What is the right autoscaling signal for the query tier versus the MCP server?

The query tier scales on RPS and latency because it serves interactive user requests under variable load. The MCP server exposes pure functions and scales on CPU utilization.

4. Why keep the deterministic dry-run evaluation suite green as model-backed adapters replace local stubs?

The suite is a regression gate. If a retrieval or synthesis change degrades answer quality, the deterministic metrics catch it cheaply in CI before the change reaches production traffic.

5. What keeps cloud deployment a configuration change rather than a code rewrite?

Provider-neutral ports and the Settings abstraction. LlmProvider, VectorStoreProvider, and adapter factories isolate cloud-specific construction so business logic does not need to change when switching between Ollama/PGVector and Bedrock/Pinecone.
